# CLAUDE.md — Optimizer Lab

Guidance for Claude Code when working in this repository. Read fully before making changes.

## What this project is

A small, self-contained Python project that builds intuition for how neural network optimizers and learning rate schedules behave. Five experiments, each producing numbers and plots that can be inspected by a non-specialist. Everything runs on CPU in under 15 minutes total; a GPU is optional.

The audience for outputs (plots, logs, README) is technically literate but **not** an ML engineer. Prefer clear labels, plain-English captions, and tables over raw tensors.

## Conventions

- **Python 3.11+**, type hints everywhere, `ruff` clean. No notebooks in `src/`; a Colab-friendly `notebooks/walkthrough.ipynb` may exist but must import from `optlab`, never duplicate logic.
- **Determinism:** every experiment takes `--seed` (default 42) and sets `torch.manual_seed`, `numpy.random.seed`, and `torch.use_deterministic_algorithms(True)`. Two runs with the same seed must produce byte-identical CSV logs.
- **No hidden hyperparameters.** Every constant (β₁, β₂, ε, λ, warmup fraction, etc.) lives in a dataclass at the top of the file with a one-line comment explaining what it controls in plain English.
- **Plots:** 150 dpi PNG, title + axis labels + a one-sentence caption rendered via `fig.text` at the bottom. Log-scale x-axis for any learning-rate axis. Never save a plot without a caption.
- **Logs:** one CSV per run in `runs/<exp>/<run_name>.csv`; columns are documented in the docstring of the writer. A `summary.json` per experiment holds the headline numbers the README quotes.
- **Do not** pull in Hugging Face, Lightning, wandb, or any heavy framework. `torch` + stdlib + matplotlib/pandas only.
- Commit messages: imperative, one line, prefixed with the experiment (`exp3: log per-layer update ratio`).

## The tiny model (shared by Exp 3–5)

`tiny_model.py` exposes `TinyLM(width: int, depth: int = 2, vocab: int = 512, seq_len: int = 64)`:
- token embedding → `depth` blocks of [LayerNorm → causal self-attention (single head is fine) → LayerNorm → MLP with 4× expansion] → LayerNorm → tied output head.
- Parameters must be grouped by name so per-layer logging works: `embed`, `block{i}.attn`, `block{i}.mlp`, `head`.
- Width must be a constructor argument so Exp 5 can instantiate 256 / 512 / 1024 with no other code changes.

`data.py` generates a synthetic sequence task (e.g. a small Markov chain or copy-with-offset task) so loss is meaningful and reproducible without downloading anything. Document the task in a docstring.

## Experiments — specs and acceptance criteria

### Exp 1 — Adam by hand
**Goal:** implement Adam's update rule in plain Python so every intermediate number is visible.

- `adam_by_hand.py` exposes `adam_step(w, g, m, v, t, lr, b1, b2, eps, bias_correction=True) -> (w_new, m_new, v_new, m_hat, v_hat)`. Pure floats, no torch.
- `exp1_adam_by_hand.py` runs one scalar weight (start `w=1.0`) through **five hand-chosen gradients** (default `[0.5, -0.4, 0.4, -0.5, 0.5]`, chosen to oscillate) with `lr=0.01, b1=0.9, b2=0.999, eps=1e-8`.
- Print a table per step: `t, g, m, v, m_hat, v_hat, step_size, w`.
- **Verify:** feed the same gradients to `torch.optim.Adam` on a single-element tensor by manually setting `.grad` each step. Assert `abs(w_hand - w_torch) < 1e-9` at every step. This assertion also lives in `tests/test_adam_matches_torch.py`.
- Output: `runs/exp1/steps.csv`, and print the table to stdout.

### Exp 2 — Bias correction on vs. off
**Goal:** show why m̂ and v̂ exist.

- Reuse `adam_step`. Run **20 steps** with a constant gradient of `+0.1`, twice: `bias_correction=True` and `False`.
- Plot `figures/exp2_bias_correction.png`: two panels — (a) step size per step for both runs, (b) weight trajectory for both runs. Caption must state in one sentence what the reader should notice (uncorrected steps start tiny and ramp up; corrected steps are consistent from step 1).
- Also write `runs/exp2/summary.json` with the step-1 step size for each variant and the ratio between them.

### Exp 3 — Weight-to-update ratio and warm-up
**Goal:** measure how much each layer actually moves per step, and find where warm-up stops being a bottleneck.

- Train `TinyLM(width=256)` with `AdamW(lr=3e-3, weight_decay=0.01)` for **300 steps**, batch 32, using linear warm-up over the first 30 steps then constant.
- After every `optimizer.step()`, for each parameter group name compute `‖Δw‖₂ / ‖w‖₂` (norm of the update divided by norm of the weight). Log to `runs/exp3/update_ratio.csv` with columns `step, group, ratio, lr`.
- Plot `figures/exp3_update_ratio.png`: log-scale y, one line per group, with the warm-up window shaded. Mark with a vertical line the first step at which every group's ratio is within 10% of its value at step 60 (i.e. the ratio has stabilized). Report that step in `summary.json` as `warmup_effect_ends_step`.
- Rule of thumb to mention in the caption: healthy ratios are roughly 1e-3 per step; much larger means the layer is being thrown around, much smaller means it is barely learning.

### Exp 4 — Cosine vs. WSD schedule
**Goal:** compare two learning rate schedules on identical models and data.

- `schedules.py` provides `cosine(step, total, peak, warmup, floor)` and `wsd(step, total, peak, warmup, decay_start, floor)` as pure functions with unit tests.
- Train `TinyLM(width=256)` **twice**, same seed, same data order, **300 planned steps** each, AdamW peak `lr=3e-3`, warm-up 15 steps, floor `lr = peak/10`:
  - Run A: cosine decay from step 15 to 300.
  - Run B: WSD — constant at peak until step 240, then linear decay to floor at 300.
- **Stop both runs at step 200** (`--stop_at 200`) and record loss at that point. This is intentional: at step 200 cosine has already decayed substantially while WSD is still flat.
- Then run both to completion (300) in a second pass so the reader can see the WSD drop.
- Plot `figures/exp4_cosine_vs_wsd.png`: two panels — (a) learning rate vs step for both, (b) training loss vs step for both, with a vertical line at 200 and the loss values annotated. Also plot the full-300 runs as dashed lines.
- `summary.json`: loss at 200 for each, loss at 300 for each, and which was lower at each checkpoint.

### Exp 5 — Learning rate sweep across widths (µP check)
**Goal:** find the best learning rate at three model widths and see whether it transfers.

- Sweep `lr ∈ logspace(1e-4, 1e-1, 13 points)` for `width ∈ {256, 512, 1024}`, 150 steps each, same seed and data. Record final loss (mean of last 10 steps) per `(width, lr)`.
- Run twice: once with standard parameterization, once with µP-style scaling from `mup.py` (scale hidden-layer init variance by `1/width` and hidden-layer LR by `base_width/width`; keep embedding/head LR fixed). `--mup` flag selects.
- Plot `figures/exp5_lr_sweep.png`: two panels (standard vs µP), loss vs lr (log x), one curve per width, **the minimum of each curve marked with a dot and labeled with its lr**.
- `summary.json`: for each parameterization, the argmin lr per width, plus:
  - `recommended_lr_4096`: the value you would use at width 4096.
  - `confidence`: one of `high | medium | low` with a one-sentence justification. Use `high` only if the three µP minima lie within a factor of 1.5 of each other; `low` if they trend monotonically with width.
- Budget guard: if a full sweep would exceed ~10 min on CPU, reduce steps to 100 and note it in the summary. Do not silently drop widths.

## Running

```
make setup      # uv sync or pip install -e .
make test       # must pass before any experiment is considered done
make exp1       # etc.
make all        # runs exp1–exp5, regenerates figures/ and runs/*/summary.json
```

## Definition of done (per experiment)

1. `make expN` runs clean from a fresh clone with no manual steps.
2. Figure exists in `figures/` with title, labels, and caption.
3. `runs/expN/summary.json` contains the headline numbers.
4. Relevant test in `tests/` passes.
5. README section for that experiment is updated with the actual numbers from `summary.json` (do not leave placeholders).

## Things to avoid

- Do not reference any course, instructor, cohort, or assignment in code, comments, README, or commit messages. This is a standalone project.
- Do not use `torch.optim.Adam` inside `adam_by_hand.py`; the whole point is that the math is visible.
- Do not "fix" an unexpected result (e.g. WSD losing at step 300) by changing hyperparameters. Report what happened and, if useful, add a short note on why.
- Do not add a GPU requirement. Use `device = "cuda" if available else "cpu"` and keep defaults CPU-feasible.
